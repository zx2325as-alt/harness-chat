P1

分析器 + 预检索并行化（投机执行）

目前流程是串行：先等分析器返回（最多 25s），再决定是否搜索，再搜索（最多 28s）。可以同时启动 analyze_complexity 和搜索，分析器返回后若不需要搜索则取消搜索任务。大多数需要搜索的 query 可节省 10-25 秒首包时间。

P2

快速缓存相似度：SequenceMatcher → embedding

_try_fast_cache_hit 用字符级编辑距离做语义匹配，similarity_threshold=0.9 要求近似完全一致才命中。「帮我写个排序」和「Python 排序怎么写」会被判不相似。改用 sentence-transformers（paraphrase-multilingual-MiniLM-L12-v2，本地免费），余弦相似度 0.85 即可命中，缓存命中率从约 5% 提升至 40%+，命中后整条链路直接返回。

命中率 +40%
P3

搜索结果会话级缓存（去重复查）

Agent 轨多轮迭代中同一 query 可能被多次调用，Refine 轨 Layer2 审查层也可能对 Layer1 已搜过的内容再次搜索。在 perform_web_search 加一个请求级 dict 缓存（key=normalize(query)，TTL=本次请求生命周期），完全相同的 query 在同一会话内复用结果，避免重复消耗 Tavily 配额和 10-15s 延迟。

P4

Fast 轨 + 分析器并发：投机 Fast 流

当分析器置信度历史上对「短问题」总是返回 fast 时，可以同时启动分析器和 fast 模型调用，如果分析器确认 fast 则直接使用已进行中的流；如果分析器返回 refine/agent 则取消 fast 流改换路径。对日常问答类查询可减少 20-25s 整体延迟。

节省 ~20s
P5

stream_slice_chars 从 8 调大到 64-128

_stream_with_fallback 和 _emit_text_chunks 每 8 个字符 yield 一次并 await asyncio.sleep(0)，对于输出 2000 字的回复需要 yield 250 次，每次都触发事件循环调度。改为 64-128 字符每片，在不影响流式体验的前提下减少协程切换开销约 75%，对 CPU 密集的 refine 轨有明显收益。

吞吐量
CPU -75%
P6

相关性过滤改为「展示后异步重排」

filter_sources_by_relevance 在搜索完成后、生成前同步调用小模型过滤，增加 1-3s 阻塞。改为：先用原始结果生成，同时后台异步过滤，等下次用户发消息时若有新查询则使用上次过滤后的缓存。或者干脆把过滤集成到 Layer2 审查层 prompt 里让审查模型自己判断哪些来源可信，省掉单独的过滤 LLM 调用。

延迟质量
节省 ~2s
P7

文档提取结果按内容 hash 缓存

/api/documents/parse 每次调用都重新提取，若用户刷新页面后重传同一文件会重做 PDF/DOCX 解析。在 extract_document 前计算 SHA256，Redis 里缓存提取结果（TTL=1小时）。对大 PDF（80页）可省去 0.5-2s 解析时间。

延迟
省 1-2s
P8

httpx 连接池参数调优

_SHARED_LIMITS 设置 max_connections=20，Refine 轨三层并发（L1+L2+L3 各自可能 fallback）加上搜索并发，实际峰值可能超过 20 导致连接等待。个人使用建议调到 max_connections=50, max_keepalive_connections=20；同时 keepalive_expiry=30s 对长时间无操作的会话可能导致连接重建，调到 60s 更合理。

P9

分析器结果按 prompt 指纹缓存（短期）

analyze_complexity 每次都调用 LLM（25s 超时），对于完全相同或高度相似的 prompt，可以用 norm_cache_prompt 作为 key，Redis 缓存分析结果 TTL=300s。重复发送同一问题（如前端重试）时直接命中，跳过整个分析层开销。

Q1

BM25 文档检索升级：混合 embedding 重排

当前 _doc_bm25_scores 纯词频匹配，对同义词、近义词、跨语言表达无效（「删除文件」≠「移除档案」）。在 BM25 初筛后用本地 embedding 模型（sentence-transformers）对 top-20 chunk 做余弦相似度重排，选 top-8 送入上下文。对文档 QA 场景答案准确率提升显著。

Q2

Layer3 润色层接收审查层输出截断 + 去元语言

审查层（Layer2）输出包含自我批评语言（「初稿存在以下问题：1. 缺少…」「修正后答案：」），这些元语言直接进入 Layer3 后润色层会在最终答案里保留批改痕迹。在 _build_layer3_prompt 里加一步正则清洗：剥除「问题清单」「初稿问题」等审查元块，只把「修正版答案」部分传给 Layer3。

极高收益最终答案质量
用户体验 +
Q3

agent_self_check 与 Layer2 review 合并

_agent_self_check_block 单独调用一个推理模型做自检，然后把结果作为 extra_review_context 注入 Layer2。这是两次串行 LLM 调用。可以直接在 Layer2 的 prompt 里加一段：「请先列出你自己对初稿的不确定之处，然后给出修正版答案」，将自检和审查合并为一次调用，对高复杂度任务节省 1 次推理时间。

Agent 历史窗口从 16 轮扩展到动态计算

_run_agent_stream 硬截取 messages[-16:]，对于复杂多轮对话会丢失早期关键上下文。应按 token 估算（每条 len(content)//4），动态选尽可能多的历史，直到总量接近模型上下文限制的 70%（给推理过程留空间）。

搜索词增强：扩展通用模式

build_search_query 增强规则只覆盖东京地名和天气类。应扩展：股票/汇率类自动加「实时 今日」；技术版本类（Vue、React、Python + 版本号）加当前年份；人名类自动去掉敬称后缀防止 Tavily 搜不到；英文 query 时避免追加中文词（目前可能把「2026年」加到英文 query 里导致搜索引擎不理解）。

_analyzer_fallback_timeout 只靠长度判断，改为多特征

reasoning_keyword_boost 扩展：代码块检测

routing_signals.py 的 reasoning_keyword_boost 只检测数学符号和逻辑词，遗漏了代码相关的复杂推理。应加入：检测是否含代码块（``` 包裹），检测是否含「debug」「报错」「traceback」等，这类 query 应路由到 reasoning 轨使用 claude-sonnet-4-6-thinking 等更强的推理模型。

Q8

Agent 重复搜索查询检测

Agent 迭代中已有 _agent_loop_ctx.last_query 记录上次查询，但只记录最后一条。若 Agent 在第 1 轮搜「A」，第 2 轮搜「B」，第 3 轮再搜「A」，不会被检测到重复。改用 set 记录所有历史查询，对语义相似（n-gram 重叠 > 70%）的新查询注入提示让 Agent 换角度，避免无效循环浪费迭代次数。

Layer1 Draft 引入来源感知 prompt

系统语言指令从硬编码中文改为动态检测

多查询并行搜索（Query Decomposition）

对于复杂 query（如「比较 A 和 B 的最新发展」），当前只发一次搜索请求。可让分析器在 search_query 字段返回数组，harness 对多个 sub-query 并行调用 perform_web_search（asyncio.gather），合并去重后的 sources 送入上下文。效果等价于手动多次搜索，但对用户透明。

F2

快速缓存 LRU 改为 Redis Sorted Set

_try_fast_cache_hit 每次扫描最多 400 条 LRU List，O(n) 复杂度。改用 Redis ZSET（score=timestamp），新增时 ZADD，扫描时 ZREVRANGE，淘汰时 ZREMRANGEBYRANK。比 LRANGE+逐条 JSON parse 快 3-5x。配合 embedding 相似度改造后，查找流程变为：先哈希精确命中 → 再 ZSET 近似扫描（向量距离）。

目前每轮搜索结果相互独立，第 3 轮提问若与第 1 轮相关但措辞不同，仍会重新搜索。可在 Redis 会话 key 里维护一个 search_knowledge_base（按 query 归档摘要），新 turn 搜索前先检索会话级知识库，命中则直接复用或追加而非全量重搜。

Refine 轨可选「仅 Layer2+3」（跳过 Draft）

content_reset 事件完整性保障

_capture_stream_text 收到 content_reset 时把 final_answer 清空，但 Redis 历史仍会等流结束后存储（此时 final_answer="" ）。若 content_reset 在流中途触发（如模型重生成），会导致 Redis 存入空字符串替换掉本次回答。应在收到 content_reset 时设置 reset_flag，等到下一个 model_end 或 [DONE] 再判断是否该存储（以 reset 后积累的内容为准）。

analyzer_total_timeout_s: 48 → 20

当前总超时 48 秒，意味着即使分析器卡住，用户要等最多 48 秒才能看到 fallback 处理开始。对个人使用场景，分析器模型（gpt-5.5）通常 3-8s 返回，analyzer_request_timeout_s=25 已经够用，total_timeout_s 建议改为 20s，减少极端情况下的等待。

C2

Layer1 temperature: 0.4 → 0.2

Draft 层的目标是「广覆盖」，但 temperature=0.4 会引入较多随机性，导致 Draft 有时包含不相关发散内容让 Layer2 要纠正的点变多，增加审查层 token 消耗。降到 0.2 可在保持覆盖度的同时减少无关发散，Layer2 审查负担降低约 20%，最终 Layer3 polish 更流畅。

C3

fast_answer_cache.similarity_threshold: 0.9 → 0.82（配合 embedding）

SequenceMatcher 下 0.9 意味着几乎完全一样才命中。改为 embedding 余弦相似度后，0.82 对应语义高度相同但措辞不同的句子，0.75 对应同主题不同角度。建议从 0.82 起用，观察一周误命中率，若无明显偏差可降到 0.78。

agent.max_iterations: 5 → 动态 3-8
